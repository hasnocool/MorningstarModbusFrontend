# v0.5 Site Digital Twin and Investigation Workbench

MorningstarModbusFrontend v0.5 turns the backend's evidence-aware component graph into an interactive site model instead of presenting topology, power flow, incidents, events, and historical telemetry as isolated pages.

## Route

```text
/site/twin
```

## What it adds

### Interactive component graph

The digital twin renders the existing read-only system component graph from:

```http
GET /v1/systems/{system_uid}/component-graph
```

The graph preserves backend evidence classes rather than inventing physical wiring:

- physical Morningstar controllers retain immutable `controller_uid` identity;
- ReadyEdge Connected Products remain reported or verified according to backend reconciliation;
- the battery bus remains a logical aggregation component;
- relationship types such as `member_of`, `charges`, and `monitors` retain source and confidence;
- configured, verified, reported, capability-derived, logical, inferred, and unknown states remain visually distinguishable.

Clicking a component opens an evidence inspector showing its backend fields, typed relationships, controller-scoped active incidents, and recent events. Physical-controller nodes link directly to their controller workspace and incident console.

### Live operating context

The page combines the graph with existing system APIs:

```http
GET /v1/systems/{system_uid}/latest
GET /v1/systems/{system_uid}/power-flow
GET /v1/systems/{system_uid}/incidents
GET /v1/systems/{system_uid}/events
GET /v1/systems/{system_uid}/stream
```

Top-level operating cards show current solar input, charge output, battery voltage/net-power evidence, controller conversion efficiency, load-power evidence where available, and active incident counts.

These values are displayed exactly according to backend semantics. The browser does not infer missing battery net power, loads, generator output, or wiring.

### Investigation workbench

The digital twin adds a synchronized multi-metric ECharts investigation surface using normalized system history:

```http
GET /v1/systems/{system_uid}/history
```

The initial correlated series are:

- `solar_input_power_w`;
- `charge_output_power_w`;
- `battery_voltage_v`;
- `battery_charge_current_a`.

The workbench supports 6-hour, 24-hour, and 7-day windows with automatic aggregation selection. System events and incident openings are annotated on the same timeline so an operator can correlate telemetry changes with charge-stage transitions, communications events, alarms/faults, retained-history activity, and persistent incident lifecycle.

Selecting **Investigate ±1h** on an active incident switches the workbench to a focused window around that incident and selects the affected controller component when the graph can resolve it.

## Why this is frontend-owned

The backend already owns all electrical semantics, evidence classification, normalized metrics, incident detection, event production, and source provenance. v0.5 deliberately does not move those rules into React.

The frontend only composes existing backend evidence into a more useful investigation workflow:

```text
incident
  -> affected component
  -> component relationships
  -> correlated telemetry window
  -> event evidence
  -> controller workspace
```

## Read-only safety boundary

The site digital twin does not add:

- Modbus register or coil writes;
- controller resets/equalization;
- alarm acknowledgement;
- controller configuration changes;
- generator controls;
- topology mutation;
- ReadyEdge/Connected Product configuration;
- SNMP SET or arbitrary protocol passthrough.

Unknown backend values remain unknown. Inferred or logical relationships are not promoted into verified physical wiring by the UI.

## Compatibility

v0.5 is based on the v0.4 Solar Day Planner branch and uses API surfaces already present in MorningstarModbusAPI v0.6+ plus the site-intelligence endpoints already consumed by the frontend. It does not require a new API endpoint.
