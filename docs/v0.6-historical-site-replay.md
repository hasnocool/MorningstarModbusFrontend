# v0.6 Historical Site Replay / Time Machine

MorningstarModbusFrontend v0.6 adds a read-only historical replay workspace at `/site/replay`.

## Goal

The Digital Twin in v0.5 answers **what is happening now?**. Site Replay answers **how did the site get here?** by synchronizing historical normalized telemetry, system events, persistent incidents, and evidence quality around one replay cursor.

## Replay workspace

The page provides:

- URL-addressable replay timestamps with `at`, `from`, and `to` query parameters.
- 6-hour, 24-hour, and 7-day replay windows.
- play, pause, single-step, and 1x / 5x / 20x replay controls.
- a global scrubber that moves all reconstructed telemetry values together.
- synchronized ECharts series for solar input power, charge output power, battery voltage, and battery charge current.
- event and incident markers on the historical chart.
- incident state reconstruction at the replay cursor using incident open/resolution timestamps.
- nearby system events around the selected timestamp.
- a two-hour before/after comparison for the four primary metrics.
- shareable replay URLs that preserve the replay window and selected timestamp.

## Evidence semantics

Replay deliberately does not fabricate a complete historical site state.

For each metric the UI selects the latest backend history bucket at or before the replay cursor only when that bucket is close enough to the selected history resolution. When the evidence is stale or absent, the value becomes `Unknown` and the card is visually de-emphasized.

The frontend does not interpolate through gaps or synthesize missing telemetry.

## Topology boundary

The current MorningstarModbusAPI component graph does not accept a historical `at=` parameter. v0.6 therefore shows the current component/relationship counts only as **present-day structural context** and explicitly states that they are not a verified historical topology snapshot.

A future backend replay contract should provide an authoritative snapshot endpoint, for example:

```http
GET /v1/systems/{system_uid}/snapshot?at=...
```

That endpoint could return timestamp-scoped components, relationships, normalized metrics, power flow, incidents, events, quality, coverage, and provenance without requiring the browser to infer historical topology.

## Existing backend APIs

v0.6 uses existing read-only APIs:

- `GET /v1/systems/{system_uid}/history`
- `GET /v1/systems/{system_uid}/events`
- `GET /v1/systems/{system_uid}/incidents`
- `GET /v1/systems/{system_uid}/component-graph`

No controller writes, configuration changes, alarm acknowledgements, topology mutations, or synthetic raw samples are introduced.

## Relationship to v0.5

v0.5 provides a live Digital Twin and investigation workbench. v0.6 turns historical investigation into a first-class workflow:

1. choose or share a time window;
2. scrub or play through recorded evidence;
3. see which incidents were active at that moment;
4. see nearby events;
5. compare the selected state with two hours earlier;
6. jump back to the live Digital Twin when present-day topology context is needed.
