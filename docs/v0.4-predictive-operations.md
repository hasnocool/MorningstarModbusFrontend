# v0.4 Predictive Operations

MorningstarModbusFrontend v0.4 adds a Solar Day Planner above the controller-native v0.2 foundation and the v0.3 incident/intelligence layer.

The goal is to answer the next operational question after live telemetry, historical analysis, and anomaly detection are already available:

> What is the rest of today likely to look like?

## Solar Day Planner

The new route is:

```text
/site/forecast
```

It consumes the backend predictive-operations endpoints:

```http
GET /v1/systems/{system_uid}/forecast
GET /v1/systems/{system_uid}/forecast/accuracy
GET /v1/controllers/{controller_uid}/charge-forecast
```

The page presents:

- current normalized site solar input;
- observed solar-input energy integrated from normalized 15-minute history;
- P10/P50/P90 remaining input-energy estimates;
- P10/P50/P90 projected end-of-day input energy;
- observed power overlaid on the P10/P50/P90 full-day historical envelope;
- progress against the expected P50 trajectory by the current time;
- a conservative all-controller probability of reaching Float;
- expected all-controller Float completion time where the backend has sufficient evidence;
- per-controller charge-state, historical Float probability, expected Float time, training-day count, and confidence;
- model provenance showing local-history source, weather usage, Internet requirement, and model name;
- historical calibration metrics including median/P90 end-of-day error and P10-P90 interval coverage.

## Uncertainty is part of the UI

The frontend deliberately does not collapse the forecast into one confident-looking number. P10, P50, and P90 remain visible so the operator can distinguish a likely midpoint from the plausible low/high range.

If the backend reports `insufficient_evidence`, the UI explains how many qualifying training days are available and does not manufacture an estimate in the browser.

## Energy semantics

The Solar Day Planner's observed/projected Wh values describe locally integrated normalized **solar-input power**. They are not silently substituted for controller-reported `daily_charge_wh` or other source-backed charging-energy counters.

The existing Energy and Energy Truth pages remain the authoritative frontend surfaces for controller/system energy accounting and provenance reconciliation.

## Charge-cycle semantics

Float probability is a historical forecast, not a controller command and not a guarantee that Float will occur. The frontend shows the current charge state, historical training counts, Float-day counts, expected historical Float time, and confidence for each controller.

The all-controller probability uses the backend's conservative aggregation rather than averaging away a weak controller outlook.

## Backtesting

The page exposes the backend's forecast-calibration summary instead of treating prediction quality as opaque. Completed days are replayed using only earlier days as training evidence.

The frontend surfaces:

- evaluated-day count;
- median absolute P50 end-of-day error;
- P90 absolute error;
- observed coverage of the P10-P90 forecast interval.

This creates a measurable path for future model improvements.

## Offline-first behavior

The first v0.4 model is intentionally local-only:

- no weather provider is required;
- no cloud inference is required;
- no Internet connection is required;
- existing SSE/polling behavior remains the live-data transport.

Future weather or irradiance inputs should be additive evidence with visible provenance, not a hidden dependency that makes the off-grid UI unusable.

## Read-only boundary

Predictive Operations does not add frontend controls for:

- Modbus writes;
- charge-stage changes;
- equalization/reset operations;
- load/generator control;
- alarm acknowledgement;
- controller configuration changes.

It is an interpretation and planning surface only.
