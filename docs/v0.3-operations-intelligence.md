# v0.3 Operations Intelligence

MorningstarModbusFrontend v0.3 builds on the controller-native/site-native v0.2 architecture and adds a
proactive operations layer backed by MorningstarModbusAPI's read-only site-intelligence resources.

## Product boundary

The frontend does not diagnose hardware independently and does not implement Modbus control. The backend
remains authoritative for detector evaluation, incident lifecycle, confidence, provenance, historical
baselines, and health-score penalties. React renders those facts and keeps the supporting evidence visible.

No frontend route writes registers, changes charge settings, acknowledges alarms, or manufactures missing
measurements.

## Operations Intelligence route

`/site/intelligence` is the site-wide operator view. It combines:

- decomposable 100-point site health score;
- active incident count and severity summary;
- active incident cards with observed versus expected values;
- expandable source/provenance evidence for every incident;
- local P10/median/P90 solar-input baseline and comparable-day count;
- 24-hour charge-cycle summaries for each physical controller;
- recently resolved incident history.

The score is deliberately not presented as a mysterious model output. Production, charging, battery,
communications, and data-integrity sub-scores remain visible and each penalty is backed by a persistent
incident.

## Controller Intelligence route

`/controllers/:controllerUid/incidents` scopes the same operations model to an immutable physical
`controller_uid`. Because the route is controller-native, an incident timeline remains stable when a USB
path, TCP endpoint, or current raw `device_id` changes.

The page includes controller health score, current and resolved incidents, charge-stage transitions,
Absorption/Float entry counts, and the collapsed 24-hour stage sequence.

The existing `/controllers/:controllerUid/intelligence` route remains the device/profile engineering view
and is labeled **Device intelligence** in navigation to distinguish the two concepts.

## Incident presentation

An incident card intentionally exposes:

- severity;
- active or resolved state;
- detector confidence;
- title and evidence-backed explanation;
- observed value;
- expected range when one exists;
- physical-controller or whole-site scope;
- open/resolution time;
- expandable evidence values and source labels.

A lack of evidence is not rendered as a recovered condition. Incident resolution is a backend lifecycle
decision made only when the detector was able to evaluate the condition again.

## Historical production baseline

The first baseline visualization is intentionally useful without cloud services. It displays the backend's
local normalized site-history comparison:

- current solar input power;
- P10 expected power;
- historical median;
- P90 expected power;
- number of comparable prior days;
- confidence and provenance.

An `insufficient_evidence` state is shown explicitly until enough comparable history exists. Weather or
irradiance can be added later as another evidence source without making the console Internet-dependent.

## Live updates

The existing system `EventSource` stream now listens for:

```text
incident_opened
incident_updated
incident_resolved
```

These events invalidate the relevant TanStack Query caches for site/controller incidents, health scores,
baselines, charge cycles, and the unified system event feed. Normal refetch intervals remain enabled as a
fallback if the SSE connection is unavailable.

This keeps the frontend asynchronous and event-driven without adding blocking browser work or tight polling
loops.

## Backend contract

The v0.3 operations UI expects these read-only MorningstarModbusAPI resources:

```text
GET /v1/incidents
GET /v1/incidents/{incident_uid}
GET /v1/systems/{system_uid}/incidents
GET /v1/systems/{system_uid}/baselines
GET /v1/systems/{system_uid}/health-score
GET /v1/controllers/{controller_uid}/incidents
GET /v1/controllers/{controller_uid}/health-score
GET /v1/controllers/{controller_uid}/charge-cycle
```

If these resources are not present, the existing v0.2 site/controller monitoring surfaces continue to work;
the Operations Intelligence view reports the intelligence resource as unavailable rather than deriving an
unsupported replacement in the browser.

## Stacked development

This change is intentionally built on the v0.2 controller-native/site-native frontend work because it uses
its `system_uid`, immutable `controller_uid`, normalized site metrics, and SSE foundations. After that
foundation lands on the default branch, the v0.3 branch can be retargeted without changing its architecture.
