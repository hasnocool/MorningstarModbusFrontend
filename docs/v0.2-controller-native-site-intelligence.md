# v0.2 Controller-Native Site Intelligence

This document defines the v0.2 frontend migration from connection-oriented controller workspaces to
immutable physical-controller and site/system workspaces.

## Goals

1. Use `controller_uid` as the canonical browser identity for one physical controller.
2. Make `/` a real site dashboard backed by the MorningstarModbusAPI system layer.
3. Use controller-scoped history, energy, export, and polling routes so endpoint changes do not split
   one controller's operational record.
4. Surface history recovery and energy reconciliation without manufacturing evidence.
5. Surface system power, energy, health, events, and topology while preserving backend quality and
   source-authority rules.
6. Use read-only SSE for lower-latency site updates without making the UI dependent on SSE availability.
7. Retain raw-device engineering views where the backend API is still explicitly device-scoped.

## Identity and routing

The canonical hierarchy is:

```text
system_uid
    |
    +-- controller_uid A
    |      +-- current device_id
    |      `-- historical device_id(s)
    |
    `-- controller_uid B
           +-- current device_id
           `-- historical device_id(s)
```

Canonical routes use `controller_uid` directly:

```text
/controllers/:controllerUid/overview
/controllers/:controllerUid/live
/controllers/:controllerUid/history
/controllers/:controllerUid/energy
/controllers/:controllerUid/registers
/controllers/:controllerUid/intelligence
/controllers/:controllerUid/diagnostics
/controllers/:controllerUid/data
```

Legacy routes remain accepted:

```text
/devices/:deviceKey/:section
```

The legacy key is decoded, matched against the current, canonical, historical, and connection device
IDs in `/v1/controllers`, then replaced with the immutable controller URL. A stale device bookmark can
therefore keep working after the physical controller has moved to another USB path or network endpoint.

## Controller-native data boundary

These frontend resources use controller-scoped routes:

| Frontend surface | Backend route |
| --- | --- |
| latest telemetry | `/v1/controllers/{uid}/latest` |
| multi-register history | `/v1/controllers/{uid}/registers/history` |
| register statistics | `/v1/controllers/{uid}/registers/stats` |
| history summary | `/v1/controllers/{uid}/history/summary` |
| evidence coverage | `/v1/controllers/{uid}/history/coverage` |
| gap reconciliation | `/v1/controllers/{uid}/history/gaps` |
| daily energy comparison | `/v1/controllers/{uid}/energy/daily` |
| energy summary | `/v1/controllers/{uid}/energy/summary` |
| streaming export | `/v1/controllers/{uid}/history/export` |
| polling performance | `/v1/controllers/{uid}/polling/performance` |

The controller latest adapter maps backend `source_device_id` into the existing `LatestSample.device_id`
compatibility field for shared presentation helpers. It does not discard the controller UID or rewrite
historical ownership in the backend.

## Device-scoped engineering boundary

The v0.6 backend still publishes register-map, device-intelligence, and profile-validation resources on
raw device routes. The frontend therefore resolves the controller's `current_device_id` for:

```text
/v1/devices/register-map
/v1/devices/intelligence
/v1/devices/profile/validation
```

This is an explicit compatibility seam rather than an accidental identity model. When the backend adds
controller-scoped equivalents, those hooks can migrate without changing canonical browser routes.

## History integrity

The History Integrity page uses two distinct evidence layers:

- persisted live polling samples;
- controller-retained daily records.

It presents:

- live-sample coverage;
- combined daily-evidence coverage;
- recovered days;
- missing days;
- recovered/partial/missing intervals from the backend gap classifier;
- a controller-scoped historical trend that spans historical raw device IDs.

A recovered day means a complete retained daily record is available where local polling is missing. It
does **not** mean the UI or backend reconstructed intra-day samples.

## Energy truth

The controller Energy page compares:

```text
controller-reported retained energy
              vs
locally integrated output_power
```

Both values stay nullable and provenance-bearing. The UI displays differences only when the backend or
available evidence supports the comparison. A missing local integration result is not replaced with the
controller daily value and vice versa.

## Site/system workspace

The site workspace consumes:

```text
/v1/systems
/v1/systems/{uid}/latest
/v1/systems/{uid}/power-flow
/v1/systems/{uid}/energy
/v1/systems/{uid}/energy-ledger
/v1/systems/{uid}/health
/v1/systems/{uid}/history
/v1/systems/{uid}/events
/v1/systems/{uid}/topology
/v1/systems/{uid}/component-graph
/v1/systems/{uid}/stream
```

### Site overview

The overview displays normalized solar input, charge output, battery voltage/current, daily energy,
controller count, health, and live-stream status. Metric quality and contributor counts remain visible.

### Power flow

Power-flow sections render backend reading objects generically so authoritative, derived, unknown, and
conflict states survive presentation. The UI never converts an unknown quantity into zero.

### Energy ledger

The energy view keeps source-backed Wh/kWh flows and native Ah counters separate. Unsupported generator,
battery-discharge, load-consumption, or loss values stay unknown according to backend semantics.

### Normalized history

System history uses the metric catalog rather than vendor register names. The selected metric and
resolution are sent directly to `/v1/systems/{uid}/history`.

### Events

The unified event view retains controller UID and event provenance rather than producing a site-wide
message with no source identity.

### Topology

The topology page shows component graph nodes/relationships separately from transport bridge candidates.
Inferred transport or electrical relationships remain labeled by confidence and are not presented as
verified physical wiring.

## SSE and query-cache behavior

The site stream is opened with `EventSource`:

```text
GET /v1/systems/{system_uid}/stream
```

On `telemetry`, the frontend invalidates system latest, power-flow, energy, energy-ledger, and health
queries. On `system_event`, it invalidates event queries.

The normal TanStack Query visibility-aware intervals remain enabled. This provides a safe fallback when:

- the browser or reverse proxy interrupts the stream;
- the API restarts;
- an older deployment does not sustain SSE;
- the tab is restored after network loss.

No blocking loop, worker thread, or browser polling timer is introduced by the SSE layer.

## Read-only safety boundary

v0.2 adds no write controls. The browser does not expose:

- register writes;
- coil writes;
- equalize/reset triggers;
- charge-state control;
- controller configuration mutation;
- generator control;
- SNMP SET;
- arbitrary Modbus passthrough.

The frontend remains an evidence and operations console. Control policy belongs outside this repository
and outside the current MorningstarModbusAPI read-only runtime boundary.

## Deferred storage UI

MorningstarModbusAPI `main` now contains Storage v2 maintenance and compressed Parquet archival, but its
operational control/status surface is currently a CLI rather than a complete read-only HTTP API. v0.2
does not invent a browser storage contract.

A future storage page should be added only after the backend publishes source-of-truth HTTP status for:

- SQLite/WAL bytes;
- archive bytes;
- reclaimable bytes;
- retention tiers;
- last verified archive;
- maintenance state and failures.

## Compatibility

The intended backend baseline is MorningstarModbusAPI v0.6+. Older deployments can still use some
inventory and raw-device engineering surfaces, but the v0.2 site and controller-history features require
the v0.6 controller/system APIs.
